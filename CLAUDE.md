# Правила разработки «Трат»

Этот файл читают все, кто пишет код в проекте, и люди, и Claude. Состояние проекта и инструкция по сборке лежат в [README.md](README.md), план по этапам в [docs/PLAN.md](docs/PLAN.md), последнее ревью в [docs/REVIEW-2026-11-14.md](docs/REVIEW-2026-11-14.md).

Приложение бесплатное и раздаётся знакомым: входа нет, данные хранятся только на телефоне. Монетизацию, аналитику и трекинг не добавлять.

## 1. Размер файлов и классов (никаких god-файлов)

- **Файл до ~400 строк.** Если правка выводит файл за 400 строк, сначала вынести часть в отдельный файл, а потом добавлять новое. Выше 600 строк не дописывать в файл вообще, только выносить из него.
- **Одна тема на файл.** Экран, его ViewModel, его карточки и диалоги лежат в разных файлах одного пакета (`ui/<экран>/`).
- **Composable-функция до ~80 строк.** Длиннее — разбить на подкомпоненты с понятными именами.
- **ViewModel обслуживает один экран.** Новая функция на другом экране — новая ViewModel, а не ещё один метод в `MainViewModel`.
- **Уже раздутые файлы** (на 15.11.2026): `ui/stats/StatsScreen.kt` (~1250), `assistant/AssistantEngine.kt` (~900), `data/Database.kt` (~840), `ui/MainViewModel.kt` (~570). Новое туда не добавлять. Когда трогаете такой файл, выносите из него хотя бы то, что меняете. Большой перенос делать отдельным PR без изменения поведения, со сборкой и проверкой на телефоне.

## 2. Архитектура

Слои и направление зависимостей: `ui → (capture | assistant) → data`. Слой `data` не знает про `ui`, а Compose не используется вне `ui/` и `widget/`.

| Пакет | Что лежит |
|---|---|
| `data/` | Room-сущности, DAO, репозитории, чистая логика расчётов (`period/`, `budget/`, `recurring/`, `insights/`…) |
| `ai/` | клиенты ИИ (`LlmClient`), промпты и разбор ответов для ввода трат |
| `assistant/` | вкладка «ИИ»: запрос → расчёт → ответ |
| `capture/` | путь «фраза → разбор → правила → сохранение» (`QuickEntry`) |
| `speech/` | распознавание речи |
| `ui/` | экраны, ViewModel, `designsystem/` |
| `widget/`, `tile/` | виджеты и плитка |

Правила:

- **Расчёты считаются в чистом Kotlin, без Android.** Функция получает данные и возвращает результат (`BillingPeriod`, `Observations`, `AssistantEngine`). Тогда её можно проверить тестом без телефона. ViewModel только собирает данные, вызывает расчёт и показывает результат.
- **Новый код ходит в базу через репозиторий** (`CategoryRepository`, `BudgetRepository`, `RecurringRepository`…), а не через `c.db.xxx()` прямо из ViewModel. Если репозитория для таблицы нет, его нужно создать. Старые прямые вызовы переводить, когда трогаете это место.
- **Общие объекты создаются в `AppContainer`** (`TratyApp.kt`). ViewModel получает их через `(app as TratyApp).container`. Синглтоны и `object` с состоянием не заводить.
- **ИИ берётся только через `container.llm(settings)`**, `clientFor` напрямую не вызывать. Тесты подменяют модель через `TestTratyApp.llm`.
- **Цифры считает приложение, ИИ только переводит вопрос в запрос и формулирует ответ.** ИИ никогда не считает суммы и не меняет данные сам: любое действие (план, подписка, запись) выполняется после кнопки подтверждения пользователя.
- **Новый провайдер ИИ** добавляется как реализация `LlmClient` в `ai/LlmClients.kt`, значение в `LlmProvider` и ветка в `clientFor`. Остальной код менять не нужно.

### Как развивать поиск ассистента

- Разбирайте отдельно действие, период, товар и его уточнения. Модель передаёт формулировку пользователя, приложение сверяет её с записями. Общие правила нормализации живут в \`data/search/\`, правила сопоставления товаров в \`assistant/\`.
- В явном вопросе о количестве сохраняйте название товара из фразы, даже если модель не вернула фильтр. При частичном совпадении покажите названия из чеков в выбранном периоде и месте. Показывайте количество и сумму выбранного варианта после нажатия на его название.
- Считайте ответ по подтверждённым позициям чека. Если нашлось только основное название, а уточнение отсутствует, показывайте отдельное предложение с ясным пояснением. Позиции с другим уточнением исключайте. Расчёт по предложению выполняется локально по тем же правилам суммы и количества.
- Перед добавлением нового правила проверьте его на вариантах названия из реальных чеков. Добавьте тесты для подтверждённого совпадения, неопределённого совпадения и похожей позиции, которую надо исключить. Проверяйте, что период и место из запроса применяются и к подсказке.
- Пока подсказки об отсутствующем вкусе используются в запросах суммы и количества. Расширяйте этот механизм по конкретным примерам. Команды изменения записей сохраняют свои правила отбора и подтверждения.

## 3. Данные и база

- **Деньги хранятся в копейках, тип `Long`.** `Double` и `Float` для сумм не использовать. Рубли получаются только при показе (`ui/Format.kt`).
- **Время в базе — epoch millis.** День и период считаются через `ZoneId` и `BillingPeriod`, с учётом дня начала периода из настроек.
- **Любое изменение схемы Room:** поднять `version`, написать `Migration(n, n+1)`, добавить её в `AppDatabase.build`, закоммитить сгенерированный `app/schemas/.../<n+1>.json` и тест миграции. `fallbackToDestructiveMigration` для новых версий запрещён: у людей там их траты.
- **Сравнение названий** делать через `sameName` / `normalizeName` (`CategoryRepository.kt`): `COLLATE NOCASE` в SQLite не понимает кириллицу.

## 4. Безопасность и приватность

- **Секреты** (ключи ИИ и всё похожее) сохранять только через `SecretCodec` (`data/secure/`), он шифрует ключом Android Keystore. Секреты не попадают в экспорт CSV, в логи и в тексты ошибок.
- **В ИИ отправлять минимум данных:** суммы по категориям, готовые факты, текст фразы. Не отправлять записи целиком, заметки и историю без нужды. Всё, что уходит в ИИ из ассистента, показывается на экране «Что ушло в ИИ».
- **Логи:** суммы, текст диктовки, названия мест и ключи пишутся только под `if (debuggable)`. В release пишутся только тексты исключений.
- **Сеть только по HTTPS.** Новые скачиваемые файлы проверяются по SHA-256, как модель речи и AAR sherpa-onnx.
- **Компоненты в манифесте** по умолчанию `exported="false"`. `PendingIntent` создаётся только с `FLAG_IMMUTABLE`.
- **Новые файлы в `filesDir`** решите сразу, переносить ли их на новый телефон, и при необходимости добавьте в `res/xml/data_extraction_rules.xml` и `backup_rules.xml`.
- **Экспорт** идёт только через системный выбор файла (SAF). Текстовые колонки CSV проходят через `CsvBackup.guardFormula`.

## 5. Интерфейс

- **Каждый экран строится на `Scaffold`**: шапка `TratyHeaderCard` с `Modifier.statusBarsPadding()` в `topBar`, контент с `.padding(pad).consumeWindowInsets(pad)`. Ничего не должно налезать на статус-бар и навигационную панель. Образец — `ui/recurring/RecurringScreen.kt`.
- **Кнопка «Добавить»** ставится в `actions` шапки, как на «Подписках», или в `floatingActionButton`.
- **Списки** — `LazyColumn`, отступы через `contentPadding` и `TratyTheme.spacing`.
- **Только дизайн-система:** цвета из `TratyTheme.colors`, отступы из `TratyTheme.spacing` (сетка 4dp), скругления из `MaterialTheme.shapes` (у полей ввода `shapes.small`), компоненты из `ui/designsystem/components`. Переключатели режимов делаются через `ModeChip` (`ui/stats/StatsModeChips.kt`). Цвета, `dp` и `RoundedCornerShape(...)` в экранах не писать числами.
- **Не ломать ручные правки вёрстки в `main`.** Перед изменением экрана посмотрите `git log` по файлу. Правки дизайна, которые Arty сделал сам, сохраняются.
- **Все тексты для пользователя пишутся по-русски**, понятными словами, без технических терминов. Ошибку показывать сообщением, приложение не должно падать.

## 6. Корутины и ошибки

- В `catch (e: Exception)` внутри корутины перед ним всегда ставить `catch (e: CancellationException) { throw e }`. Флаги «загрузка» сбрасывать в `finally`.
- Тяжёлая работа (база, файлы, сеть, Keystore) выполняется вне главного потока (`Dispatchers.IO` / `Default`, `flowOn`).
- `!!` не использовать. Неожиданный ответ сервера оборачивать в понятную ошибку (`textAt` в `LlmClients.kt`).
- Сетевые ошибки ввода трат (`IOException`) ставят фразу в очередь, а не теряют её. Не ломать это различие в `QuickEntry`.

## 7. Тесты

- **Любая новая логика приходит с тестом** в `app/src/test/...` в том же пакете. Чистые функции проверяются обычным JUnit, ViewModel — через Robolectric и `TestTratyApp` (база в памяти).
- Запуск: `./gradlew :app:testDebugUnitTest`.
- **Облачные сессии не собирают приложение**: Android SDK не скачивается. В облаке чистая логика проверяется через `kotlinc` и JUnit. В PR честно писать, что нужно собрать и проверить на телефоне, и по каким шагам.

## 8. Git и PR

- Небольшие PR по одной теме. Рефакторинг (перенос, переименование) отдельно от изменения поведения.
- Сообщения коммитов и описания PR пишутся по-русски: что изменилось для пользователя и почему.
- В описании PR есть раздел «Проверить на телефоне», если затронуты экраны, база, Keystore, голос или виджеты.
- Крупную переделку, которую нельзя проверить сборкой, сначала описать как предложение, а не делать вслепую.
