# Этап 2 — Голос и быстрый ввод: дизайн

Дата: 2026-11-14. Этап 2 в [PLAN.md](../../PLAN.md).

## Зачем

Трата (или пополнение) добавляется за 3–5 секунд голосом, не открывая приложение: с виджета или плитки в шторке. Распознавание речи — на телефоне (GigaAM v3), без отправки голоса наружу. Главный экран упрощается до одной большой кнопки микрофона: ИИ сам понимает, что сказано — трата или пополнение, и сколько операций в фразе.

**Готово, когда:** на разблокированном телефоне через виджет или шторку фраза вида «кофе 250, такси 400 и пришла зарплата 80 тысяч» сохраняется правильно в 9 случаях из 10.

## Цели

1. Встроенное офлайн-распознавание GigaAM v3 (sherpa-onnx + Silero VAD) как реализация `SpeechEngine`.
2. Одна общая «точка ввода»: главная, плитка и виджет используют одну цепочку «запись → разбор → автосохранение / подтверждение → сохранение».
3. Смешанные фразы: несколько операций, у каждой ИИ определяет `type` (`expense` | `income`).
4. Автосохранение уверенных трат без экрана подтверждения.
5. Плитка Quick Settings и виджет Glance.
6. Очередь фраз без сети с фоновым разбором.

## Не цели

- Работа на заблокированном экране (без разблокировки). Только разблокированный телефон; `showWhenLocked` не используем. Плитка на заблокированном телефоне вызывает `unlockAndRun`.
- Текст «по буквам» в реальном времени — GigaAM не потоковая модель, промежуточный текст появляется кусками между паузами.
- Типы `goal_deposit` / `debt_payment` — этап 6 (но формат `type` закладывается расширяемым).
- Ручной ввод текстом и ручная трата «+» на главной.

## Анти-цели (провал, даже если «работает»)

- Автосохранение молча сбивает баланс: пополнение или неуверенная трата сохранились без проверки.
- Обновление приложения стирает историю (миграции Room обязательны).
- Каждое обновление APK весит сотни МБ (модель не встраиваем в APK).
- С плитки/виджета каждый раз открывается всё приложение целиком.

## Ограничения

- minSdk 26, target/compile 35. Room сейчас версии 6 → новая миграция 6→7.
- Запись с микрофона можно начать только из видимой активити (ограничения Android 14+ на фоновый микрофон) → плитка и виджет открывают лёгкую активити записи, а не пишут звук сами.
- На Android 14+ `TileService.startActivityAndCollapse` принимает `PendingIntent`; для 24–33 — `Intent`.
- Разрешение `RECORD_AUDIO` уже в манифесте; запрашивать в рантайме при первом нажатии.
- DI — ручной `AppContainer` в [TratyApp.kt](../../../app/src/main/java/ru/my/traty/TratyApp.kt). Новые сервисы регистрируются там же.
- Принцип «минимум данных наружу»: в ИИ уходит только распознанный текст + список категорий/правил (как сейчас).

## Подходы (выбрано: 1А + 2А)

### 1. Движок распознавания

| | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **А ✅** | **sherpa-onnx** (готовая Android-библиотека, JNI) с моделью GigaAM v3 в формате sherpa + Silero VAD | GigaAM и VAD поддерживаются из коробки, звук → текст кусками по паузам; +10–15 МБ нативного кода (только arm64-v8a) | нужна модель именно в формате sherpa |
| Б | Голый ONNX Runtime + своя обвязка | любая выгрузка GigaAM, в т. ч. с пунктуацией | самим писать мел-спектрограмму, RNN-T-декодер, VAD; несколько вечеров, ошибки малозаметны |
| В | Vosk | ~45 МБ, проще всего | заметно хуже качество русского, а GigaAM выбран ради качества |

### 2. Быстрая запись

| | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **А ✅** | Отдельная лёгкая активити-панель поверх текущего приложения + общий класс «движок ввода», вынесенный из `MainViewModel` | плитка/виджет не открывают приложение; логика одна для всех точек входа | нужно вынести логику из `MainViewModel` |
| Б | Всё через `MainActivity` с флагом | меньше кода | каждый раз открывается всё приложение — против цели этапа |

Пользователь согласился с обоими выборами.

## Решения пользователя

1. Только разблокированный телефон.
2. На главной внизу — только большая красивая кнопка микрофона (GigaAM). Убираются: кнопка «+» (ручная трата), переключатель «трата / пополнение» (`incomeMode`).
3. ИИ сам определяет тип каждой операции; в одной фразе может быть несколько операций, смешанных трат и пополнений.
4. Правило автосохранения (предложено, принято): **сразу сохраняется фраза, только если все операции в ней — траты, у каждой есть сумма и сработало правило «место → категория»**. Если в фразе есть пополнение или хоть одна неуверенная трата — открывается экран подтверждения всей фразы. После автосохранения — снекбар «Сохранено N · Изменить».
5. Предложенное и принятое (playback):
   - поле ввода текста с главной убирается — правки делаются на экране подтверждения;
   - чипсы шаблонов остаются над кнопкой микрофона;
   - один общий разбор вместо `ExpenseParsing` + `IncomeParsing`, поле `type` у каждого элемента;
   - один общий экран подтверждения со смешанным списком и переключателем типа у строки (заменяет `ConfirmDialog` + `IncomeConfirmDialog`);
   - пока модель не скачана — кнопка временно вызывает системное распознавание (`SystemSpeech`);
   - панель записи: открылась → сразу запись → автостоп по паузе ~1,5 с → автосохранение или подтверждение прямо в панели;
   - кнопка на главной использует ту же логику записи;
   - виджет: большая 🎤 + суммы «сегодня / месяц»; плитка: «Сказать трату»;
   - без сети фраза (уже распознанная офлайн) ставится в очередь; на главной карточка «N фраз ждут разбора»; при появлении сети — фоновый разбор с тем же правилом автосохранения, остальное — карточка «Разобрано, проверьте». Простой офлайн-разбор для сохранения без сети **не** используется;
   - модель GigaAM v3 int8 (~210–230 МБ) скачивается при первом включении с Hugging Face с прогрессом в настройках; запасной путь — ручное копирование файлов в папку приложения; модель грузится в память только на время записи.

## Как устроено

### Компоненты

```
speech/
  SpeechEngine            — интерфейс (уже есть), события: partial(кусок), final(текст), error, level(громкость)
  GigaAmEngine            — sherpa-onnx OfflineRecognizer + Silero VAD; AudioRecord 16 кГц mono;
                            каждый VAD-сегмент → распознавание → partial; пауза ~1,5 с после речи → final + stop
  SystemSpeechEngine      — обёртка над RecognizerIntent (запасной, пока нет модели)
  ModelManager            — состояние модели (нет / качается N% / готова / ошибка), скачивание, проверка файлов
capture/
  QuickEntry              — общий «движок ввода»: текст → разбор → правила → решение (автосохранение / подтверждение / очередь) → сохранение
  ParsePolicy             — чистая функция правила автосохранения (тестируется юнит-тестами)
  PendingPhrase + DAO     — очередь фраз без сети (Room)
  PendingParseWorker      — WorkManager, constraint NetworkType.CONNECTED
ai/
  EntryParsing            — единый промпт и decode: items[{type, amount, category, emoji, subcategory, place, note, source, date}]
ui/capture/
  CaptureActivity         — прозрачная активити-панель (bottom sheet) поверх приложений
  RecordPanel             — Compose: большая кнопка, волна/уровень, промежуточный текст, подтверждение
  EntryConfirmSheet       — общий экран подтверждения смешанного списка
widget/   TratyWidget (Glance), TratyWidgetReceiver
tile/     VoiceTileService
```

### Единый разбор

- Один запрос к ИИ, ответ `{"items":[{"type":"expense"|"income", ...}]}`. Поля траты — как в `ParsedExpense`; поля пополнения — `source` из `IncomeSources`. Неизвестный `type` → `expense`.
- Правила «место → категория» применяются к элементам `expense` (как `applyRules` сейчас).
- `OfflineParser`/`OfflineIncomeParser` остаются только для варианта «ИИ не настроен» (нет ключа): тогда текст разбирается простым парсером, тип — по словам «зарплата / аванс / пришло / вернули / дежурства», и **всегда** открывается подтверждение.
- Ошибка ИИ при наличии сети (не сетевая: 4xx/битый JSON) → простой разбор + подтверждение (как сейчас). Сетевая ошибка/нет сети → очередь.

### Решение после разбора (`ParsePolicy`)

```
нет сети / сетевая ошибка                → очередь (PendingPhrase)
все items.type == expense
  и у каждой amount > 0
  и у каждой сработало правило           → автосохранение + снекбар «Сохранено N · Изменить»
иначе (есть income, нет правила, пусто)  → экран подтверждения всей фразы
```

**Что значит «сработало правило» (моё решение, по итогам проверки):**
- Совпадение ищется только в `place` и `note`, которые вернул ИИ. Название категории в поиск не входит. Сейчас `applyRules` ищет и в названии категории, и правило «кафе» совпадало бы с любой тратой в категории «Кафе». Это исправить.
- Если правило совпало, его категория побеждает ответ ИИ: так работает и сейчас.
- Правила продолжают отправляться в промпт: это помогает ИИ в неуверенных случаях. Но для автосохранения считается только локальное совпадение.

«Изменить» после автосохранения открывает экран подтверждения с уже сохранёнными операциями; правка заменяет их (удалить сохранённые id → вставить новые) в одной транзакции.

### Очередь без сети

- Таблица `pending_phrases`: id, text, createdAt (время произнесения — дата операции по умолчанию берётся от него, а не от момента разбора), status (`waiting` | `parsed` | `failed`), resultJson?, error?. Migration 6→7.
- `PendingParseWorker` при появлении сети разбирает `waiting`; уверенные — сохраняет и удаляет фразу; остальные → `parsed` с результатом.
- На главной: карточка «N фраз ждут разбора» (waiting) и «Разобрано, проверьте» (parsed) → открывает экран подтверждения.

### Главная

- `TratyInputBar` заменяется большой кнопкой микрофона по центру; над ней чипсы шаблонов; под ней строка промежуточного текста во время записи.
- Убираются `input`, `incomeMode`, `manualDraft`, переключатель типа из UI и ViewModel; разбор и сохранение делегируются `QuickEntry`.
- Запись на главной идёт прямо в экране (без открытия `CaptureActivity`), тем же `QuickEntry` + `SpeechEngine`.

### Панель записи (CaptureActivity)

- Прозрачная тема, `excludeFromRecents`, отдельный `taskAffinity`, `launchMode=singleInstance`; не запускает `MainActivity`.
- Открылась → нет разрешения: запросить; нет модели: системное распознавание → сразу запись.
- Автостоп по паузе; кнопка — ручной стоп; тап вне панели / «назад» — отмена.
- После решения: автосохранение → снекбар в панели на ~2 с с «Изменить» → закрыть; подтверждение → `EntryConfirmSheet` в той же панели; очередь → «Нет сети, разберу позже» → закрыть.
- После сохранения обновить виджет.

### Виджет и плитка

- Glance-виджет: кнопка 🎤 «Сказать трату» → `CaptureActivity`. Под ней две суммы **расходов**: «сегодня» и «за текущий расчётный период» с учётом дня начала периода из настроек. Считаются так же, как «Расходы» в шапке главной, включая записи сверки «Неучтённые». Пополнения и баланс в виджет не выводятся. Это моё решение: виджет отвечает на вопрос «сколько я уже потратил». Обновление после каждого сохранения и раз в сутки.
- `VoiceTileService`: тап → (заблокирован? `unlockAndRun`) → `startActivityAndCollapse(CaptureActivity)`.

### Модель GigaAM

- Формат: GigaAM v3, сконвертированная для sherpa-onnx, int8 + Silero VAD (~2 МБ, можно положить в assets APK).
- **Какая именно модель (решение по итогам проверки).** Официальных сборок v3 у sherpa-onnx на момент написания нет: у них есть только v1 и v2 (transducer и CTC). Сторонние выгрузки v3 есть. Порядок такой:
  1. Основной кандидат — GigaAM v3 e2e CTC int8 (~305 МБ, со знаками препинания) от ProtocolVoice. По их описанию, модель загружается через sherpa-onnx. Первым делом этапа 4 нужен короткий пробный запуск: модель грузится в `OfflineRecognizer` на телефоне и распознаёт тестовые фразы.
  2. Если v3 не грузится или распознаёт плохо — официальная GigaAM v2 от sherpa-onnx (CTC или transducer). Это запасной вариант.
  3. Свою конвертацию и подход Б (ONNX Runtime со своей обвязкой) не делаем.
  - Лицензия весов GigaAM некоммерческая. Для личного приложения без публикации это допустимо.
  - `ModelManager` должен описывать модель манифестом (список файлов + размеры/хэши + тип модели для sherpa), чтобы смена v3 ↔ v2 не меняла код.
- Хранение: `filesDir/models/gigaam-v3/`. Скачивание по HTTPS с Hugging Face, во временный файл → проверка размера/хэша → переименование. Прогресс и «Удалить модель» — в настройках, раздел «Голос».
- Выбор движка в настройках: GigaAM / системный (по умолчанию GigaAM, если модель готова).
- Загрузка модели в память при старте записи, освобождение после `final` (держать ~30 с на случай повторной записи — на усмотрение исполнителя).

## Оставлено исполнителю

- Точный артефакт модели и URL (выбрать конвертированную под sherpa-onnx GigaAM v3, RNN-T или CTC — по качеству/размеру на телефоне), способ подключения sherpa-onnx (AAR из релизов в `libs/` или Maven-артефакт, если есть).
- Порог паузы VAD (стартово 1,5 с), максимальная длина записи (стартово 30 с).
- Визуальное оформление кнопки микрофона и панели — в стиле текущей дизайн-системы (`TratyTheme`).
- Срок жизни модели в памяти после записи.
- Где хранить флаг «сработало правило» для `ParsePolicy` (например, в результате `applyRules`).
- Порядок реализации внутри этапа; рекомендованный: (1) единый разбор + `QuickEntry` + общий экран подтверждения + новая главная на системном распознавании → (2) `CaptureActivity` + плитка + виджет → (3) автосохранение + очередь → (4) GigaAM + `ModelManager`.
- Тесты: юнит-тесты `ParsePolicy`, `EntryParsing.decode`, миграции 6→7; остальное — ручная проверка на устройстве.
